# Cairn

> [English](README.md) · [Для агентів](#робоче-правило-для-будь-якого-агента) · [Докази](docs/CAIRN_RELEASE_EVIDENCE.md) · [Apache-2.0](LICENSE)

**Cairn зберігає історію правки для наступного агента.**

Git показує, що змінилося. Чат може пояснювати чому, але агент, який
редагував код, уже завершив сесію, його контекст стиснуто або журнал лишився
на іншому пристрої. Cairn поєднує історію Git, вузли проєкту й доступні
сесії агентів у локальному сховищі `.cairn`. Перед новою правкою агент може
побачити попередні рішення, підтверджені зміни та вилучений текст.

Інструмент працює з будь-яким Git-репозиторієм. Цифри нижче отримано на
самому репозиторії Cairn як першій контрольній зоні релізу.

## Що змінюється для команди агентів

```text
Людина й агент узгоджують зміну
    → агент редагує файл → Git-коміт, одразу або пізніше
    → сесія може стискатися → Cairn зберігає доступні докази
    → інший агент запитує історію файла перед своєю правкою
```

OpenCode, Claude Code і Codex через адаптери журналів можуть поповнювати
одне сховище проєкту. Cairn бере **завершені правки**, а не `grep`, читання
файла чи команду, яка тільки обіцяє правку. Він зберігає підсумок сесії,
якщо той існує, і прямо повідомляє про його відсутність. Збіг переходу
тексту може пов'язати правку з пізнішим комітом, навіть зробленим в іншій
сесії.

Наприклад, у виміряній історії `cairn_unified/why.py` є сім Git-комітів.
Для `dc0f95e` Cairn знайшов одну підтверджену правку сесії та п'ять
вилучених рядків. Для `17dfc19` — чотири підтверджені правки й 33 вилучені
рядки. Наступний агент бачить ці зміни разом із записаним наміром і межею
доказу. Збіг вмісту доводить участь правки в коміті; він не доводить мотив
автора або те, хто виконав `git commit`.

## Виміри на цьому репозиторії

Зріз: `dc0f95eee70f0ba31e18555e96b3f64adeca6ef5`, 2026-11-22.
Метод і машинозчитувані результати є в
[доказовому звіті](docs/CAIRN_RELEASE_EVIDENCE.md) та
[його JSON-записі](docs/CAIRN_RELEASE_EVIDENCE.json).

| Перевірка | Результат |
|---|---:|
| Git-коміти, наявні в `.cairn` | **26/26** |
| Історичні коміти `cairn_unified/why.py` | **7/7** |
| Коміти з підтвердженими правками сесій | **10/26** |
| Коміти лише з Git-контекстом | **16/26** |
| Унікальні правки, пов'язані з комітом | **94** |
| Перевірені за Git зв'язки правок із комітами | **115/115**, зокрема 21 старий повторний зв'язок |
| Повторний синк без нових змін джерела | **0** нових подій; той самий digest |
| Повний набір тестів | **31/31**; один приватний необов'язковий тест пропущено |

Число `10/26` **не означає «коміти Claude Code»**. Серед цих десяти комітів
два мають підтверджені правки Claude Code, чотири — OpenCode, сім — Codex.
Один коміт може містити правки кількох агентів, тому сума більша за десять.
Решта 16 — справжні зміни Git, але завершену журнальну правку не вдалося
однозначно зіставити з ними. Ім'я автора Git не визначає, який агент
редагував файл.

Ось скільки тексту повернули два фіксовані дослідження `why.py`.
Для обох шляхів використано однакову приблизну оцінку:
**кількість символів ÷ 4**.

| Питання | Без Cairn: Git-текст, прочитаний скриптом | З Cairn: усі виміряні виклики | Кінцева відповідь `why` |
|---|---:|---:|---:|
| Чому файл змінив `dc0f95e` | ≈52 113 токенів | ≈2 351 токенів | ≈1 546 токенів |
| Чому файл змінив `17dfc19` | ≈52 277 токенів | ≈2 705 токенів | ≈1 900 токенів |

**Шлях з Cairn повернув приблизно у 19–22 рази менше тексту**, ніж саме
цей Git-прогін. Git-шлях читав `log -1`, статус файлів, 12 патчів і `blame`;
він дав сировину, **не** незалежно написану рівноцінну відповідь. Уважний
агент може прочитати менше Git-тексту. Тому вимір показує розмір саме цих
двох шляхів, а не універсальну економію токенів. Cairn працював локально
приблизно 0,83–0,91 с, Git-команди — близько 0,19 с. Перевагу в швидкості
ми не заявляємо.

Головна користь для кількох агентів — неперервність. Наступний агент отримує
типізовану історію від усіх проіндексованих агентів і не відновлює зв'язок
між чатами, правками та комітами з нуля. Повноту видно одразу:
**16 із 26 комітів** поки мають лише Git-контекст.

## Робоче правило для будь-якого агента

Позначення в командах:

- `<REPO>` — Git-проєкт, історію якого потрібно зберегти;
- `<ROOT>` — тека зі сховищем `.cairn` цього проєкту;
- `<CAIRN>` — checkout коду Cairn з текою `tools/`;
- `<BUNDLE>` — **приватний** шлях до пакета поза публічним Git;
- `<WORKTREE>` — необов'язковий другий checkout **того самого** репозиторію.

1. **Перед правкою файла** звір Git HEAD і прочитай його історію. Якщо
   `freshness.status` дорівнює `stale`, спочатку синхронізуй сховище.
   Поточний код прочитай окремо: Cairn його не повертає.

   ```text
   git -C <REPO> rev-parse HEAD
   python -m cairn_unified --root <ROOT> why node <relative/path> --repo-path <REPO>
   ```

2. **Після завершеної правки, коміту або компактації сесії** запусти синк
   із `<CAIRN>`. За потреби один раз створи сховище. Кожний доступний
   worktree додай окремим `--source-repo`; якщо він один, другого не треба.

   ```text
   python -m cairn_unified --root <ROOT> project init
   python -m cairn_unified --root <ROOT> repo add <REPO>
   python tools/sync_project_causality.py --root <ROOT> --repo <REPO> --source-repo <REPO> --bundle <BUNDLE>
   ```

3. **Перевір доведене.** Коміт лише з Git-контекстом справді змінив файл,
   але правку агента до нього не прив'язано. Не вигадуй відсутню сесію й
   не вважай пізнішу компактацію доказом ранішого мотиву.

   ```text
   python tools/link_mutations_to_git.py --root <ROOT> --repo <REPO> --verify
   python -m cairn_unified --root <ROOT> project doctor
   python -m cairn_unified --root <ROOT> why node <relative/path> --repo-path <REPO> --commit <SHA>
   ```

4. **На іншому пристрої** віднови приватний пакет у клоні тієї самої
   Git-історії, а потім синхронізуй локальні журнали агентів цього пристрою.
   Не публікуй пакет: у ньому є слова людини й агента. Повний експорт
   блокується, якщо сховище містить кілька зон репозиторіїв.

   ```text
   python -m cairn_unified federation restore <BUNDLE> <CLEAN_CLONE>
   python -m cairn_unified --root <CLEAN_CLONE> project doctor
   ```

[Мандат агенту](MANDATE-AGENT-CAIRN-CAUSAL-HISTORY.md) містить точні правила
доказу. [Підключення агента](AGENT-ONBOARD.md) та
[інтеграція](docs/INTEGRATION.md) описують CLI і MCP. У Windows PowerShell
встанови `PYTHONIOENCODING=utf-8`, якщо консоль не виводить Unicode.

## Як зберігаються дані

`.cairn` — локальне сховище. Джерело істини — журнал подій, що тільки
доповнюється; SQLite є проєкцією для читання, яку можна відбудувати. Git
дає тотожність комітів і diff. Адаптери читають локальні журнали й зберігають
доступні причинні докази. Звичайне читання й пошук не додають історичних
подій. Приватний переносний пакет містить самі події, а не символічні
посилання на локальні журнали. Пакет Python використовує стандартну
бібліотеку й надає CLI та 12 MCP-інструментів.

## Поточні межі

- Докази сесій неповні: підтверджені правки агентів мають лише 10 із 26
  виміряних комітів. Для решти Cairn показує Git-факти, не вгадуючи причину.
- Ім'я акаунта в журналі не є криптографічним доказом особи.
- Локальне відновлення й повторний імпорт перевірено. Реальне злиття двох
  пристроїв із різними новими комітами та підтримувану Unix-платформу ще
  потрібно перевірити.
- Публічний реліз містить числовий доказовий звіт. Сирі сесії й переносний
  пакет залишаються приватними. Для сховища з кількома зонами потрібен
  окремий зональний експортер.
- У поточному текстовому дереві немає машинних шляхів, але всі 26 старих
  Git-комітів іще їх містять. Публікація повної Git-історії потребує окремого
  рішення про її очищення; релізний аудит зараз блокує цей варіант.
  Source snapshot без `.git` не переносить стару історію користувачам.
