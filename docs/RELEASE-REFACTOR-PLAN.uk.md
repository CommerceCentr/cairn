# План доведення Cairn до релізу

Поточний контрольний зріз і релізні межі див. у
[CAIRN_RELEASE_EVIDENCE.md](CAIRN_RELEASE_EVIDENCE.md). Текст нижче фіксує
початковий план і виміри до контрольного коміту `dc0f95e`.

Початковий стан на 2026-11-22: публічний і приватний checkout мали незакомічені зміни. Публічний пакет уже містив `cairn_unified.adapters.codex`, а приватний checkout ще тримав стару теку `adapters/`. Приватна SQLite-проєкція мала версію 2, тоді як приватний код очікував 1; публічний код очікував 3. Журнал подій є джерелом істини, SQLite — похідна проєкція. Цей документ зберігає план, а поточний статус наведено в доказовому звіті.

Цільова модель: **одне спільне сховище**, де сесії OpenCode, Claude Code і Codex співіснують із репозиторіями, комітами та вузлами. `commit_fact --mutated--> node` доводить Git; `node --caused_by--> session` допускається лише за структурованою завершеною мутацією, яка потрапила до вузлів саме вказаного коміту. `read`, `grep`, пошук і перегляд не створюють історичних ребер. Сесія Codex без структурованої мутації може мати область вузлів із явно повʼязаного коміту для пошуку в хронології; це не твердження про причину правки.

## 1. Зафіксувати базу

1. Зберегти `git status --short`, поточні SHA та diff обох checkout. Відділити роботу користувача від релізних змін.
2. Обрати публічний checkout Cairn як кодову базу релізу. Перенести потрібні приватні виправлення по одному, з оглядом diff. Не копіювати `.cairn/`, локальні шляхи, журнали сесій чи секрети в публічний репозиторій.
3. Зафіксувати підтримувані версії Python та контракт даних адаптерів. Єдине місце адаптерів у пакеті — `cairn_unified/adapters/`; усунути імпорти з верхньорівневого `adapters`.

## 2. Узгодити сховище

1. Зробити копію всієї приватної `.cairn/` поза робочою проєкцією; перевірити хеші журналу та manifest до будь-якої перебудови.
2. На копії виконати `python -m cairn_unified --root <копія-проєкту> project rebuild` кодом обраного релізного checkout. Перевірити `project doctor`, кількість подій, ланцюг журналу і повторюваність результату rebuild.
3. Лише після збігу результатів перебудувати робочу SQLite-проєкцію. Версію в manifest і коді узгоджувати через штатний rebuild, не ручним редагуванням SQLite.

## 3. Довести адаптери

1. Кожен адаптер повертає лише події, які доводить джерело: `user_intent`, `compaction`, `reasoning`, `mutation`; стабільні `event_id`, `session_id`, час і походження обовʼязкові.
2. Codex: читати rollout JSONL і JSONL.zst лише на читання; підтримувати `CODEX_HOME` та домашню теку; відкидати службові user-блоки; гарантувати різні ID за відсутності `ordinal`.
3. Структуровані правки можна додати як мутації лише після звірки виклику інструмента з успішним результатом і точними шляхами. Shell/PowerShell/JavaScript не вважати доказом правки за текстом команди. До появи такого доказу Codex чесно повідомляє `mutation=unsupported:shell_embedded`; привʼязка до коду спирається на Git-факти.
4. Привʼязку сесії запускати з явно заданими `--root`, `--repo`, `--commit`, `--source codex`, `--journal`. Автовибір журналу дозволяти лише коли його `cwd` або workspace roots збігаються з репозиторієм; неоднозначність має бути помилкою, а не випадковим вибором.
5. Для журналу поза стандартним `CODEX_HOME/sessions` встановити `CAIRN_CODEX_SESSION_ROOTS` на каталог журналу. Параметр `--journal` додає цей каталог до пошуку на час імпорту й перевірки; для пізнішої повторної верифікації змінну потрібно встановити знову. Абсолютний шлях не записується до переносного обʼєкта.

## 4. Релізні ворота

1. Unit-тести: формат журналу, компактація, інʼєктовані блоки, порожні/биті рядки, повторний імпорт, Unicode, кілька коренів, відсутній `ordinal`.
2. Інтеграція: копія спільного сховища, один реальний журнал Codex і один коміт; перевірити ідемпотентність, `project doctor`, provenance, межі довіри та відсутність витоку сирого журналу в експорт.
3. Запустити повний `tests/run_all.py`, зібрати wheel, встановити в чисте середовище та повторити CLI/MCP smoke tests. Перевірити Windows PowerShell і підтримувану Unix-платформу.
4. Синхронізувати README, архітектуру, інтеграційний посібник і changelog з фактично перевіреними можливостями. Після цього зробити релізний commit і tag; без зелених воріт статус лишається pre-release.

## Використання зараз

```powershell
$env:PYTHONIOENCODING='utf-8'
python -m cairn_unified --root <STORE_ROOT> project doctor
python -m cairn_unified --root <STORE_ROOT> mcp tools
python tools/link_agent_session.py --root <STORE_ROOT> --repo <REPO> --commit <sha> --source codex --journal <rollout.jsonl> --verify
```

Остання команда записує у сховище. Її запускати після узгодження схеми та на точно вибраній сесії; параметр `--commit` повинен називати справді повʼязаний коміт.

## Виміри 2026-11-22

- Копію приватного `.cairn` з тим самим SHA-256 `events/ledger.jsonl` перебудовано публічним кодом: 1 876/1 876 подій; `project doctor` пройшов, схема SQLite 3.
- Початковий повний прогін у sandbox зупинився на `PermissionError` при створенні тимчасових тек Python. Дозволений прогін після всіх змін дав 27/27; приватний `verify_auto_dossier` штатно позначено `SKIP`.
- Синтетичний Codex rollout на копії сховища з явно заданим комітом: 2 канонічні події, 941 вузол коміту при першому імпорті, 0 недоведених `caused_by`; після виправлення ключа `unresolved_mutations` усі 4 обʼєкти пройшли перевірку. Повторний імпорт залишив число подій незмінним: 2 860 → 2 860.
- Синтетичний rollout є тестом механіки, а не свідченням того, що реальна Codex-сесія створила цей коміт.
- У 80 реальних rollout-файлах знайдено 15 відкритих `compacted` і 19 зашифрованих `response_item/compaction`. Адаптер зберігає факт зашифрованої компактації, але її текст лишається порожнім і позначається `encrypted_compaction`.
- На коміті `9feecdf` старий алгоритм позначав 941 вузол із 56 змінених файлів. Звірка діапазонів рядків і захист від незакомічених правок залишили 226 вузлів. Адресний тест підтвердив: змінена функція входить до набору, сусідня незмінена — ні; брудний файл знижується до адреси цілого файла. Для історичного коміту, де поточні номери рядків уже ненадійні, також використовується тільки адреса цілого файла.
- Чистий наскрізний Codex імпорт на копії приватного сховища: 1 876 вихідних подій; після індексації, 226 `mutated` та чотирьох перевірених обʼєктів — 2 120 подій, `project doctor: ok=true`. Після ще однієї локальної правки коду повторна індексація додала один `code.indexed`; наступний імпорт без зміни файлів залишив 2 121 → 2 121 подію. Отже, ідемпотентність перевірено для незмінного робочого дерева.
- Робоче приватне `.cairn` скопійовано до `_release_scratch/live_backup_20261122/.cairn` (30 файлів, 38 096 490 байтів); SHA-256 manifest і журналу збігаються. Публічним кодом відтворено його SQLite-проєкцію: 1 876/1 876 подій, схема 3, `project doctor: ok=true`; SHA-256 журналу після перебудови не змінився. MCP `cairn_semantic_query` відкрив сховище, число подій залишилось 1 876.
- `tools/serve_shared_cairn.py` пройшов stdio smoke: `initialize` і `tools/list` повернули 12 інструментів. У локальний конфіг Codex додано `[mcp_servers.cairn]` після резервної копії; TOML пройшов синтаксичну перевірку. Доступність сервера всередині вже відкритої розмови Codex окремо не підтверджена.

У цьому історичному вимірі приватний checkout ще містив старий `cairn_unified` зі схемою читача 1. Для роботи з перебудованим сховищем слід було запускати CLI/MCP із публічного checkout Cairn, доки перенесення приватних змін не завершиться. Резервну копію й тестові копії не включати в публічний реліз.
